### Security-header modification

`rules.json` removes these response headers for ChatGPT main/sub frames:
- `X-Frame-Options`
- `Content-Security-Policy`
- `Cross-Origin-Opener-Policy`
- `Cross-Origin-Embedder-Policy`

This is materially more invasive than a minimal UI helper and weakens normal browser/page isolation controls while the rule is active.

## Custom-GPT compatibility finding

The live A1 screenshot already proved that the AutoGPT panel loads on the `MYGPT Single Frame Worker Test` Custom-GPT page.

Static code supports that finding:
- ChatGPT detection is generic to `chatgpt.com` rather than a separately hard-coded ordinary-chat-only route.
- no explicit Custom-GPT `gizmo` / GPT-ID-specific implementation was found.
- the new-chat implementation for regular ChatGPT clicks the page DOM element `a[data-testid="create-new-chat-button"]` and waits for the UI.

Interpretation:
- the extension does not appear to create a fresh Custom-GPT chat through a dedicated hidden Custom-GPT API;
- it relies on the ChatGPT page's own new-chat UI control;
- therefore preserving the current GPT identity depends on how that control behaves on the current `/g/...` page.

A1 activation compatibility is therefore a real PASS, but A3 fresh-chat identity preservation still requires a live test if this extension itself is ever used.

## Prompt submission and canonical image upload

For regular ChatGPT, the extension contains direct DOM-level automation:
- finds the unified composer form;
- pastes text into the prompt editor using synthetic clipboard events;
- submits through synthetic UI/key behavior;
- uploads files through the page's existing `input[type=file]` by assigning a `DataTransfer` file list and dispatching a `change` event.

This is important for MYGPT: the core primitives needed for canonical upload and one-packet submission can be implemented without a separate OpenAI API.

The ChatGPT file-input path is distinct from the extension's separate `imgbb` upload helper used by other workflows/platforms. No evidence was found that the normal ChatGPT `gptUploadImages()` path sends the canonical image through imgbb before attaching it to ChatGPT.

## Internal ChatGPT API interception — production concern

The full extension is not merely UI automation.

It monkey-patches `window.fetch` and watches ChatGPT internal endpoints including:
- `/backend-api/conversation`
- `/backend-api/f/conversation`
- internal attachment / file-download endpoints

For ChatGPT conversation requests, it reads the outgoing prompt body and captures a `Bearer` Authorization header into extension runtime state.

It then clones/reads ChatGPT streaming responses to detect generation progress/completion and generated asset information.

Separate helper functions directly call internal ChatGPT endpoints such as:
- conversation retrieval
- file-download metadata retrieval

using the captured Authorization value.

This is a materially different risk profile from merely opening tabs and clicking visible UI controls.

## Output extraction / automated download

The bundle contains logic to:
- parse generated-image/file metadata from ChatGPT responses;
- track conversation / asset identifiers;
- read internal file-download responses;
- obtain download URLs;
- invoke the extension background worker to download output;
- provide auto/batch-download behavior.

Therefore the installed product's full operating model includes programmatic output extraction, not only prompt submission.

For MYGPT, these parts are unnecessary for the first orchestration goal and should not be copied into a minimal automation design.

## Visibility / focus behavior modification

`scripts/inject.js` modifies page-observable browser state for supported platforms including ChatGPT:
- intercepts visibility/page lifecycle events;
- exposes `document.visibilityState` as `visible`;
- exposes `document.hidden` as `false`;
- replaces `document.hasFocus()` with a value that reports focus.

This appears intended to keep automation operating when the page is backgrounded.

MYGPT does not need this for a conservative first implementation. Do not copy it unless a later named failure proves it necessary.

## External account / membership traffic

The extension contains multiple Autojourney API fallback origins:
- `apijourney.autojourney.top`
- `apijourney.autojourney.ai`
- `apijourney.zeabur.app`
- `apijourney.kingback.app`

Membership checks POST to `/api/checkAuth/isMember`.

The extension extracts the logged-in ChatGPT user's identity information from ChatGPT page bootstrap data (`CLIENT_BOOTSTRAP` / `gptUserDefer`). For the ChatGPT path, the membership request can include the account email or bound email.

This explains why the live Plan modal was able to display the ChatGPT-account email without the user manually entering it into that modal.

## Analytics / privacy finding

The installed bundle directly posts Google Analytics Measurement Protocol events to:
- `https://www.google-analytics.com/mp/collect`

The analytics event parameters include a field named `discord_user_email` populated from the extension's current stored user email getter. On ChatGPT, that getter is populated from the ChatGPT account identity path.

The UI also records events such as extension view/page view; the page-view event includes `location.href` as `page_location`.

Therefore, in ordinary technical terms, the installed code contains telemetry capable of transmitting:
- the account email used by the extension on the ChatGPT path;
- the active page URL;
- membership state / event metadata

to Google Analytics.

This finding should not be conflated with the Chrome Web Store developer disclosure categories, but it means the extension is not a zero-telemetry local-only helper.

## Other external upload helper

The bundle contains an `api.imgbb.com` image-upload helper that appends an email field.

However, the regular ChatGPT image-upload implementation uses ChatGPT's local file input path, so this helper is not evidence that MYGPT's canonical image is automatically sent to imgbb during the normal ChatGPT worker flow.

## Plan gating

The ChatGPT feature set is marked member-only in the bundle and membership is checked remotely against Autojourney infrastructure.

Therefore the live `Activate AutoGPT Plan` modal is not only cosmetic UI; full task automation is gated by the extension's membership state.

## Revised N3 implication

The earlier UI-only HOLD remains justified for the full AutoGPT product, but static analysis changes the engineering conclusion:

**Do not abandon browser automation. Do not copy/use the full extension as the production worker orchestrator. Extract only the proven low-risk primitives into a minimal local implementation.**

Useful prior-art primitives verified in code:
1. ChatGPT Custom-GPT page can host browser-extension controls.
2. new-chat can be driven by the visible ChatGPT DOM control.
3. prompt text can be placed through the visible composer.
4. canonical files can be attached through the existing ChatGPT file input.

Do NOT carry over into the MYGPT minimal implementation:
- ChatGPT fetch/XHR interception;
- Bearer Authorization capture;
- direct `backend-api` calls;
- streaming-response parsing;
- generated-output extraction or download automation;
- security-header removal;
- visibility/focus spoofing;
- automatic retry/rate-driving logic;
- Autojourney membership/account calls;
- Google Analytics telemetry;
- third-party image upload.

## Recommended next experiment

Build or prototype a local, narrow browser helper for `/g/...` that initially does only one non-generation operation:

1. open a fresh `MYGPT Single Frame Worker Test` conversation through the visible UI / Custom-GPT route;
2. verify the GPT identity remains unchanged;
3. place one harmless text payload into the composer or clipboard;
4. leave final submission manual for the first safety gate.

Only after this passes should file attachment and three-worker fan-out be added one primitive at a time.

This path preserves the validated Custom-GPT isolation architecture while avoiding the invasive parts found in AutoGPT 0.0.71.
