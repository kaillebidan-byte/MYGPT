# 流用可能部分の整理

## そのまま採用する生成原則

### 1. 画像生成を主処理にする

画像生成依頼では、長い説明、工程説明、許可確認を先に返さない。必要な入力が揃っている場合は、画像生成Capabilityを直接使う。

出典となる設計:

- gptstore-promptsのimage generator
- Zennの手書き温もりイラスト画像ジェネレーター
- 公開DALL·E系GPTに共通する直接実行方針

### 2. 添付画像をキャラクターの正本にする

ユーザーが添付した画像を、キャラクターの見た目を決める主要参照として扱う。

維持対象:

- 顔、目、髪
- 衣装、配色、模様、装飾
- 頭身、体格、手足の比率
- 線、塗り、陰影、素材感
- 所持品と固有パーツ

出典となる設計:

- PocketMonster-style image generationの「元の特徴を維持しながら動的な変化を加える」構造
- Consistent Character Image Generatorの「同じキャラクターで変化だけを作る」構造

### 3. 可変部分を限定する

単発依頼では、ユーザーが指定した次の要素だけを変更する。

- 表情
- 動作
- ポーズ
- 視線
- 必要な付随動作

背景、衣装、画風、体格などは、明示されない限り変更しない。

### 4. 曖昧さを合理的に補う

生成を妨げない軽微な不足は既定値で補う。確認質問は、結果が大きく変わる条件が欠けた場合だけにする。

単発モーション依頼の既定値:

- キャラクター: 添付画像
- 動作: ユーザーが指定した動作
- 構図: 元画像を基準に全身が切れない構図
- 背景: 元画像を維持。素材用途が明らかな場合は透明
- 画像数: 1枚
- 説明文: 最小限

### 5. 修正は局所的に行う

修正依頼では、指摘された要素だけを変更する。問題のない顔、衣装、配色、構図、画風を再設計しない。

## 条件付きで採用する部分

### 連続画像とスプライト

複数フレームやスプライト生成は、単発画像生成とは別モードにする。

単発の「手を振るモーションを作って」という依頼を、常に8フレームのスプライトシートへ拡張しない。依頼文にフレーム、ループ、スプライト、アニメーション素材などの指定がある場合だけ、複数フレームモードへ入る。

### 生成後の監査

監査は画像生成成功後にのみ実行する。監査開始失敗を画像生成失敗として扱わない。

ただし、生成画像をGPT Actionへ直接渡す仕組みは2026年時点で不安定な報告があるため、運用版では次の条件を満たすまで必須化しない。

1. 現行モデルで生成画像の`openaiFileIdRefs`が自動注入される。
2. 外部から取得可能な一時HTTPS URLが渡される。
3. GitHub側がURL失効前に取得できる。
4. GPTが監査完了待ちで生成結果を取り消さない。

## 不採用とする部分

### seed値の保存と再利用

Consistent Character Image Generatorには、初回画像のseedをCode Interpreterへ保存し、次回以降へ再利用する指示がある。

これは現在のCustom GPTの組み込み画像生成で、利用者が制御できる機能として保証されていない。実行不能な命令を入れると、画像生成を止めたり、存在しないファイル操作へ逸れたりするため採用しない。

### 常に4枚生成する対話フロー

MYGPTの主な依頼は単発モーションである。性別、名前、年齢、スタイルを順番に質問し、4枚生成する公開GPTの対話フローは用途に合わない。

### 過剰な秘匿・拒否命令

公開設定に含まれる、InstructionsやKnowledgeの開示要求を大量に拒否する規則は画像生成品質に寄与しない。長い禁止列挙は生成ツール実行より優先される可能性があるため採用しない。

### 固有作品・ブランドの画風指定

公開GPTに含まれる固有作品名は、構造調査のための例としてのみ扱う。運用版では、ユーザーのオリジナルキャラクターの画風を参照画像から維持する。

### 旧DALL·E固定寸法

1024×1024、1792×1024などをInstructionsへ固定しない。現行のChatGPT画像生成Capabilityが扱うサイズとUIに任せ、素材仕様として厳密な寸法が必要な場合だけ後処理・監査側で扱う。
