# 実運用から見えるパターンと失敗

調査日: 2026-08-07

これは設計決定ではなく、複数の実運用例を比較した観察メモ。

## 1. Projectは「共有コンテキスト + 複数チャット」で使う

成功例では、1 Projectに1つの長大な会話を置くより、共通のInstructionsとSourcesを持たせ、作業単位ごとにチャットを分けている。

例:

```text
Project
  Instructions
  Sources
  chats/
    research
    design
    generation-test
    review
```

用途や成果物が変わったらチャットを分ける。会話が長くなり指示追従が崩れた場合も、新しいチャットで正本から状態を再構成する例がある。

## 2. Instructionsは「毎回変わらない規則」に寄せる

実例でInstructionsへ置かれていたもの:

- Projectの目的
- ChatGPTの役割
- 判断基準
- 文体/出力形式
- 不明点の扱い
- 情報源の優先順位

一方、具体的な案件データ、長い参考文章、過去作品、テンプレート、設定表などはSourcesへ分離する例が多い。

## 3. Sourcesは巨大な一冊より、小さい正本へ分割する

長期運用の利用者は、巨大なmaster documentより、subject別/用途別の小さい資料へ分ける方法を採っている。

例:

```text
README.md
rules.md
character.md
motion.md
output-spec.md
```

必要な資料が明確になり、新しいチャットで「この作業ではA/B/Cを参照」と指定しやすい。

## 4. 会話履歴を正本にしない

長期Projectでは、会話そのものを唯一の状態保存先にすると、指示ドリフト、古い判断の混在、ファイル参照の不安定さが問題になったという報告がある。

実践的な対策として、GitHub等の外部ファイルをdurable stateとして持ち、確定事項をそこへ戻す運用がある。

MYGPTで既にGitHubを正本にしているため、この考え方は相性がよい。ただし採用判断は別途行う。

## 5. Project Sourcesを「必ず毎回答で全文再読するDB」とはみなさない

公式にはProject filesはProject内のコンテキストとして利用される。一方で実利用者からは、長いやり取りの途中で参照を外したり、ファイルが使えないと回答したり、期待したsource-bound behaviorにならないという報告がある。

したがって、高精度が必要な処理では、次のような運用が候補になる。

- 重要な資料を短く保つ
- ファイル名と役割を明確にする
- タスク開始時に参照対象を明示する
- 長いチャットを引き延ばさない
- 確定状態を会話だけに残さない

## 6. Projectを分ける基準は「テーマ」だけではなく「規則」

一部power-userの整理では、同じ作業規則を共有できる仕事を同じProjectに置き、必要な規則が違うなら別Projectへ分ける。

例えば画像生成Projectなら、キャラクター生成、モーション素材生成、一般的な調査を全部混ぜるのではなく、Project Instructionsが一貫する範囲を一つのProjectとして考える。

## 7. Project-only memoryは作成前に考える

公式仕様と利用者報告では、project-only memoryはProject作成時の重要な設定であり、既存Projectを後から簡単に切り替えられない場合がある。

他の会話や別案件の記憶を混ぜたくない用途では、Project作成時点で隔離方針を決める必要がある。

## 8. 画像はテキストSourcesと同じ感覚で扱わない

キャラクター参照画像をProject filesへ置いても、視覚情報として期待通り利用されなかったという過去の実験報告がある。一方、チャットへ直接画像を添付すると認識されたという報告がある。

この挙動は時期やモデルで変わり得るため、Project Sources上の画像だけでキャラクター同一性を保証する設計は、実機検証なしに採用しない方がよい。

## 9. キャラクター画像では「基準へ戻る」運用が見られる

画像生成の実践者からは、生成物を何世代も連続編集すると一致性が低下するため、以下のような方法が共有されている。

```text
character sheet / baseline image
        ↓
新しい生成A

character sheet / baseline image
        ↓
新しい生成B

character sheet / baseline image
        ↓
新しい生成C
```

Aを元にB、Bを元にCと連鎖させるより、毎回同じ基準へ戻る考え方。

## MYGPT設計時に検証すべき事項

まだ決めず、Project版の実機テストで確認する項目:

1. Project Sourceへ置いたPNGをThinkingが実際に視覚参照できるか。
2. 同じPNGをチャットへ直接添付した場合との差。
3. Project Instructionsが新規チャットでも安定して適用されるか。
4. 3つ程度の短いMarkdown Sourcesを毎回正しく参照できるか。
5. 同じチャットを長く続けた場合、何ターン程度で指示/資料参照が崩れるか。
6. 新規チャットへ切り替えた場合、Project Sourcesだけで作業状態を再構築できるか。
7. character sheetと単一基準画像のどちらが同一性維持に強いか。
